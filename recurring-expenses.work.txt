============================================================
WHAT WAS IMPLEMENTED
============================================================
- Recurring rules: amount, category, description, frequency (weekly, every 2 weeks, monthly, yearly),
  start date, optional end date, paused flag, and a "generatedThrough" date (how far generation has got).
- Scheduling (pure, in lib/recurring.ts):
  - occurrenceDate(schedule, n) always computes from the start date, so monthly/yearly month-end
    clamping never drifts: Jan 31 -> Feb 28 (Feb 29 in leap years) -> Mar 31 -> Apr 30. Yearly Feb 29
    -> Feb 28 in non-leap years.
  - occurrencesBetween(schedule, after, through, limit) honors the end date. It starts from an estimated
    index, so a rule that began decades ago doesn't step from occurrence 0 every time.
  - nextOccurrence(rule) returns the first occurrence after generatedThrough, or null once the rule
    has ended.
- Generation (generateDueExpenses, pure):
  - Creates ordinary Expense objects for every occurrence due on or before today.
  - Ids are deterministic: "recurring:<ruleId>:<YYYY-MM-DD>". recurringExpenseId(),
    parseRecurringExpenseId() and isGeneratedByRule() trace an expense back to its rule.
  - Each occurrence is created exactly once, by two mechanisms:
    (1) the per-rule generatedThrough watermark only moves forward, so a generated expense the user
        deleted or edited is never recreated;
    (2) existing ids are skipped, so a run with stale rules (StrictMode double effects, two tabs loading
        at once) can't add duplicates.
    When a run isn't capped, it advances generatedThrough to today. Rule edits therefore apply only to
    future occurrences, and the form says so.
  - Runaway guard: MAX_GENERATED_PER_RUN = 200, shared across all rules. A capped run sets the watermark
    to the last generated date and reports capped=true. The user sees an info toast with a "Continue"
    action, and the rest is also generated on the next load. The add form warns ahead of time when a
    start date would backfill more than 200 expenses, and otherwise shows how many past expenses will be
    added.
  - Generation runs on app load (once, guarded by a ref, and idempotent anyway), after a rule is created
    or edited, after a resume, and when the tab becomes visible again (which covers the date changing
    while the app is open).
  - If saving the expenses to localStorage fails, the rule watermarks are not advanced, so the next load
    generates those expenses again instead of losing them.
- Pause/resume: paused rules generate nothing. Resuming skips occurrences missed while paused
  (watermark = yesterday) but still generates today's. A toast says that missed occurrences were skipped.
- Delete: a dialog shows how many expenses the rule has already created and offers three choices:
  Cancel, "Delete rule, keep expenses", or "Delete rule and N expenses". If the rule created nothing,
  it shows a single "Delete rule" button. The success toast has Undo, which restores the rule and any
  removed expenses.
- UI:
  - New /recurring page (RecurringView) lists each rule with its category icon, description, schedule
    text, the number of expenses created so far, the amount, and the next occurrence
    ("Next Nov 30, 2026", "Paused", "Ended", or "(catching up)" while capped).
  - Edit, Pause/Resume and Delete are icon buttons with descriptive aria-labels.
  - Shows an empty state and a loading skeleton.
  - The rule form (RecurringRuleForm) follows ExpenseForm's patterns: labels tied to inputs,
    aria-invalid/aria-describedby, errors shown after blur or submit, focus moves to the first invalid
    field on submit, data-autofocus works with the native <dialog>, keyboard-accessible category radios,
    and a native <select> for frequency.
  - Validation messages cover amount (required, format, > 0, <= $1,000,000), category, description
    (required, <= 100 chars), frequency, start date (required, valid, >= 1900-01-01, within 10 years
    from today; future starts are allowed), and end date (valid, not before the start date).
- Storage: rules use their own key "expense-tracker:recurring:v1". parseStoredRules() drops malformed or
  duplicate rules and counts them (toast: "N invalid recurring rule(s) were skipped."), and reports an
  error for corrupt JSON or a non-array value instead of throwing. Rules sync across tabs via the
  "storage" event.
- Conventions followed: local YYYY-MM-DD strings with parseISODate/toISODate, roundToCents, the form keeps
  amount as a string until toRecurringInput(), CATEGORIES/CATEGORY_META, the native <dialog> Modal, and
  every expense mutation goes through ExpenseProvider's commit().

============================================================
KNOWN LIMITATIONS
============================================================
- Rule edits never backfill. Moving the start date earlier, or changing the frequency, doesn't create
  occurrences on or before the last generation date (normally today). Changes apply from tomorrow on.
- Occurrences missed while a rule was paused are skipped on resume, not backfilled (by design).
- A start date decades in the past fills in 200 expenses per run. The user continues via the toast's
  "Continue" action or on later loads; for example, a weekly rule from 1990 takes about 10 runs.
- Generation runs on load, after rule save/resume, and on visibilitychange. A tab left visible across
  midnight won't generate the new day's occurrence until one of those happens.
- Cross-tab writes are last-writer-wins, as in the existing app. Duplicate generated expenses are
  impossible because ids are deterministic. An unrelated edit made in another tab at the same instant
  could still be overwritten, as before.
- The Expenses list and dashboard don't visually mark generated expenses. You can only tell them apart
  by id, which CSV export doesn't include. A badge in ExpenseList would be easy to add but would touch
  another shared component.
- After "Delete rule, keep expenses", the kept expenses still carry the recurring id prefix of a rule
  that no longer exists. This is harmless.
- The UI was not exercised in a browser; it is only verified by typecheck, lint and build.
