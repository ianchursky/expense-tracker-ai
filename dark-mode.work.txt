WHAT WAS IMPLEMENTED
- Three theme choices: System (default; follows prefers-color-scheme and reacts live to OS changes via a
  matchMedia "change" listener), Light, Dark.
- Navbar theme control (components/layout/ThemeMenu.tsx): an icon menu button following the WAI-ARIA
  menu-button pattern. The trigger has aria-haspopup="menu", aria-expanded, and aria-label
  "Theme: <current choice>", so the current choice is announced. Items are role="menuitemradio" with
  aria-checked. Keyboard: Enter/Space/ArrowDown/ArrowUp open it; ArrowUp/ArrowDown/Home/End move between
  items; Enter/Space choose; Escape closes and returns focus to the trigger; Tab closes; clicking outside
  closes. Focus starts on the checked item. The trigger icon shows the resolved theme (sun/moon), or a
  neutral monitor icon before load so it matches the server render.
- The preference is saved to localStorage under a versioned key. If storage is unavailable (reads or writes
  throw) it falls back to System and the choice lasts only for the current page load. Invalid or missing
  values parse to System. Open tabs stay in sync through the "storage" event.

HOW FLASH-OF-WRONG-THEME IS PREVENTED
- app/layout.tsx renders <script dangerouslySetInnerHTML={{ __html: THEME_INIT_SCRIPT }} /> in <head>. It
  runs synchronously before the body is parsed or painted. It reads the stored preference (with try/catch),
  treats anything other than light/dark as system, resolves system through
  matchMedia("(prefers-color-scheme: dark)"), and toggles the "dark" class on <html>. color-scheme follows
  from that class through CSS, so nothing else needs setting. The whole script is wrapped in try/catch.
- <html> has suppressHydrationWarning because the class differs from the server HTML by design.
- ThemeProvider reads the same state in a mount effect and only starts writing the class once it has
  loaded (isLoaded), so its pre-load defaults never undo what the script applied. After that, it toggles
  the class on preference changes, OS changes and cross-tab storage events.
- A test runs the script string against fake window/document objects for every stored value
  (missing, valid, invalid) and both OS settings, and checks it agrees with parseThemePreference and
  resolveTheme. That guards against the two drifting apart.
- Verified in the build output: .next/server/app/index.html contains the inline script and both
  theme-color meta tags. The compiled CSS contains the :is(.dark *) variants, the
  dark:backdrop:bg-black/70 ::backdrop rule, and :root.dark{color-scheme:dark}.

CHART THEMING APPROACH
- Recharts takes colors as props, so lib/theme.ts exports
  CHART_COLORS: Record<"light" | "dark", { grid, tick, cursor, bar }>.
  Light keeps the original values: #e2e8f0, #64748b, #eef2ff, #6366f1.
  Dark uses #334155 (grid), #94a3b8 (ticks), #1e293b (hover cursor), #818cf8 (bars).
- MonthlyTrendChart reads CHART_COLORS[useTheme().resolvedTheme] and passes the colors to CartesianGrid,
  the XAxis/YAxis tick props, the Tooltip cursor and Bar.
- Tooltips are custom HTML content components, so they use dark: classes. The donut keeps the category
  hex colors, which stay legible on the dark card. Its legend and center label are HTML with dark: classes.
- Charts render only after expenses load, which happens in the same mount pass as the theme, so they
  should not appear with the wrong palette.
