WHAT WAS IMPLEMENTED
- "Back up (JSON)" button on the Expenses page header. It downloads ALL expenses (filters are ignored) as a versioned JSON document named expense-tracker-backup-YYYY-MM-DD.json (local date), then shows a toast.
- "Restore from backup" button in the Expenses page header and in the empty state, so a fresh browser can restore. It opens an app-wide native <dialog> owned by ExpenseDialogProvider (same pattern as the add/edit form and the confirm dialog).
- Restore dialog flow:
  1. A labelled file input ("Backup file (.json)", accept .json) with a hint. It gets initial focus through data-autofocus.
  2. The file size is checked before reading (10 MB limit). The text is then parsed and validated by lib/backup.ts. Document-level errors appear in a role="alert" box.
  3. Preview as readable text (a <dl> in a role="status" region): file name, exported-at time, valid records, new, identical duplicates, conflicts (with how many are newer in the backup), and invalid records. Invalid records are listed in an expandable <details> as "Record N (index i): reason", capped at 50 rows; the count stays exact.
  4. Strategy radio group (fieldset/legend):
     - Merge: adds new records. For a conflict it keeps the copy with the later updatedAt; on a tie it keeps the current copy.
     - Replace all: deletes the current data and loads the backup's valid records.
     The merge button is disabled when the merge would change nothing.
  5. Merge applies immediately. Replace all opens the existing app-wide confirm dialog ("Replace all expenses?"), which stacks above the restore dialog. Cancel returns you to the preview.
  6. Every restore is one complete list written in a single commit() (never partial). The success toast offers Undo, which writes back the exact previous array snapshot.
- Robustness:
  - Rejects: empty files, non-JSON, a non-object or wrong "format", a missing, non-integer or < 1 version, a future version (> 1), a missing "expenses" array, input over 10 MB (checked on File.size in the UI and on text length in the lib), and more than 50,000 records.
  - Each record is validated with the app's own form rules: validateExpenseForm() plus toExpenseInput(). That means a real local YYYY-MM-DD date that is not in the future and not before 1900, a category in CATEGORIES, an amount that is a positive finite number with at most 2 decimals and no more than 1,000,000, and a trimmed description of 1 to 100 chars (whitespace normalized the same way the form does).
  - Records also need a non-empty id (max 200 chars) and parseable createdAt/updatedAt.
  - A repeated id inside the file is reported as invalid. Unknown fields are stripped.
  - Bad records are reported and skipped; they never fail the whole import.

BACKUP FILE FORMAT
{
  "format": "expense-tracker-backup",      // exact string, required
  "version": 1,                            // integer >= 1, required
  "exportedAt": "2026-10-28T14:03:00.000Z",// UTC ISO timestamp (informational; ignored if invalid)
  "count": 3,                              // informational only, not enforced
  "expenses": [                            // required array, max 50,000 entries
    { "id": "uuid", "date": "YYYY-MM-DD", "amount": 12.5, "category": "Food",
      "description": "Lunch", "createdAt": "ISO", "updatedAt": "ISO" }
  ]
}
- The file is pretty-printed with 2-space indentation. Records are full Expense objects in stored order.
- Versioning rules: BACKUP_VERSION is bumped whenever the document shape changes. parseBackup must keep reading every older version (migrate inside parseBackup). Versions above BACKUP_VERSION are rejected with "made by a newer version of the app". The backup version is independent of the localStorage key version (expense-tracker:expenses:v1).
- Record identity is "id". "Identical duplicate" means every field is equal, including createdAt and updatedAt.

KNOWN LIMITATIONS
- Records dated in the future are rejected, the same as the form. A backup made in a timezone ahead of yours, containing an expense for "today", could have that record rejected; it is reported, not silently dropped.
- Records whose amount has more than 2 decimals are rejected rather than rounded.
- The size check in the lib uses string length (UTF-16 code units). The UI checks the real File.size first.
- localStorage is about 5 MB. A large restore can exceed the quota: commit() then shows the existing "Couldn't save" error toast and the in-memory state still holds the restored list (existing app behavior for any mutation). No Undo toast is shown in that case.
- Undo restores the snapshot taken at apply time. Edits made in another tab between the restore and clicking Undo are overwritten by Undo.
- "count" in the file is not cross-checked against expenses.length.
- The "Delete all" confirmation text still says "Export a CSV first if you want a backup". It was left unchanged to avoid conflicts; consider pointing it to "Back up (JSON)" after merging.
